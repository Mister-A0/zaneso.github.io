01
PART 1

XSS Definition and the Three Types

#

The lecture defines XSS as a vulnerability that allows attackers to run JavaScript in web applications. It is one of the most commonly found bugs in web applications, and its difficulty ranges from easy to extremely hard depending on how the target application parses input. The deck distinguishes three types along four dimensions: where the payload is injected, where it executes, how long it persists, and what triggers it[cite: 2].

Type Injection point Execution Persistence
DOM-based (special) URL fragment or DOM sink Entirely in the browser DOM; typically uses a script or iframe tag None (per request, but client-side)
Persistent (stored, server-side) Any field the server stores Server renders the stored payload to each viewer High; fires for every viewer
Reflected (client-side) URL parameter or form field Server reflects the payload back in its response None; single request and response

The lecture also covers reconnaissance before exploitation. Students browse the application through Burp Suite with interception turned OFF, so every request is captured in HTTP History for later analysis. This is passive reconnaissance: no payloads are sent, and it connects directly to the Week 3 enumeration methodology[cite: 2]. The recommended workflow is to configure the browser to route through Burp at 127.0.0.1:8080, set interception to OFF, browse normally (log in, search, post, navigate), review HTTP History, and map the attack surface: forms, URL parameters, custom HTTP headers, and hidden routes. Interception should be turned ON only when a request must be modified, because it blocks each request and slows reconnaissance[cite: 2].

🧠
KNOWLEDGE CHECK 1
Tests three points: DOM-based XSS is the type that executes entirely in the victim's browser (answer C), passive reconnaissance uses interception OFF (the statement that interception ON is recommended is false), and Persistent XSS differs from Reflected XSS because the payload is stored on the server and fires for every visitor, whereas Reflected XSS is bundled into a single request and fires only when the victim submits or clicks the crafted link[cite: 2].

PART 2

Exploiting DOM-Based XSS

#

The verified payload is an iframe whose src attribute is a javascript: URI[cite: 2]:

Payload
<iframe src="javascript:alert(`xss`)">

The deck notes that using an iframe to execute a javascript: URI is also called XFS (Cross-Frame Scripting) and is one of the most common ways to detect XSS in web applications[cite: 2].

Technique steps:

  1. Locate a search bar or any input field whose value is reflected into the DOM without encoding[cite: 2].
  2. Paste the iframe payload into the search field and submit[cite: 2].
  3. The browser parses the iframe, encounters the javascript: URI scheme, and executes alert(`xss`)[cite: 2].

Why it works: it is common for a search bar to send a request to the server and display the related results. The flaw is that, without correct input sanitisation, the search bar can be used to perform an XSS attack[cite: 2].

General rule: any application that allows user modification of iframes or other DOM elements is a likely XSS candidate. Auditors should check every location where user input reaches a DOM sink, such as innerHTML, document.write, eval, or iframe src[cite: 2].

🧠
KNOWLEDGE CHECK 2
Covers the element used (an iframe whose src is a javascript: URI), the fact that XFS is a recognised alias for this technique, and why the search bar is a viable attack surface even though the server returns the response. The attack surface is the DOM the browser builds from the server's response, so the flaw is the lack of input sanitisation[cite: 2].

PART 3

Exploiting Persistent (Stored) XSS

#

This part uses the "Last Login IP" page in Juice Shop, and the technique is injected through an HTTP header rather than a visible form field[cite: 2].

Attack walkthrough:

  1. Log in to the Juice Shop account normally[cite: 2].
  2. Navigate to the Last Login IP page, which shows the IP address from which the account last logged in[cite: 2].
  3. Log OUT, but first enable Burp interception ON so the logout request is captured before it reaches the server[cite: 2].
  4. In the captured logout request, add a custom HTTP header: True-Client-IP: <iframe src="javascript:alert(`xss`)">[cite: 2].
  5. Forward the modified request. The server logs the malicious IP value as part of the logout record[cite: 2].
  6. Log back in and revisit the Last Login IP page. The stored payload fires in the browser[cite: 2].

Why it works: the True-Client-IP header is similar to X-Forwarded-For, since both tell the server or a proxy the client's IP address. Because no sanitisation is applied to this header value, injecting a payload into it and having the application later display it, unsanitised, triggers stored XSS[cite: 2].

Teaching point: Persistent XSS injection points are not limited to obvious form fields. HTTP headers that are logged and later displayed are equally valid vectors. These include Last Login IP, User-Agent, Referer, X-Forwarded-For, and True-Client-IP. Auditors should check every location where stored data is later rendered[cite: 2].

🧠
KNOWLEDGE CHECK 3
Asks why the True-Client-IP injection succeeds (the server stores the value and renders it without sanitisation), states and corrects the claim that Persistent XSS is limited to traditional form fields (false, because any stored and displayed data can serve as an injection point), and asks students to name two abusable headers. The model answers are True-Client-IP and X-Forwarded-For, which are typically not sanitised because developers assume they contain a benign IP address string[cite: 2].

PART 4

Exploiting Reflected XSS

#

This part uses the Order History tracking page in Juice Shop. The payload is identical to Parts 2 and 3. Only the injection point changes, and the new vector is the id parameter[cite: 2].

Attack walkthrough:

  1. Log in to Juice Shop and navigate to the Order History page[cite: 2].
  2. Click the tracking icon for any order. This opens a tracking-result page whose URL contains an id parameter, for example 5267-f73dcd000abcc353[cite: 2].
  3. Replace that id value with the iframe payload: <iframe src="javascript:alert(`xss`)">[cite: 2].
  4. Submit the modified URL by pasting it into the address bar and pressing Enter[cite: 2].
  5. Refresh the page. The alert fires[cite: 2].

Why it works: the server looks up the tracking ID against a lookup table or database. Because the id parameter is not sanitised before being reflected back into the page, the injected payload executes. This is the defining trait of Reflected XSS: the payload travels out in the same request and response cycle, so the victim must submit or click the malicious link or URL[cite: 2].

Request and response cycle:

Step Actor What happens
1 Attacker Crafts a malicious URL with the payload in the id parameter[cite: 2]
2 Victim Clicks or submits the URL[cite: 2]
3 Server Looks up the id in the database[cite: 2]
4 Server Reflects the payload back into the response page, unsanitised[cite: 2]
5 Browser Parses the HTML and executes the payload (alert)[cite: 2]
🧠
KNOWLEDGE CHECK 4
Tests the single-request nature of Reflected XSS (answer C), states the false claim that Reflected XSS fires automatically for every visitor, and asks why the attacker must trick the victim into clicking a link or submitting a form. The answer is that the payload is not stored, so it must travel in the request itself, which is why Reflected XSS usually depends on phishing or link shortening[cite: 2].

PART 5

Cross-Site Request Forgery (CSRF)

#

Source note: the CSRF material in this lecture comes from standard academic and OWASP coverage, not from the Juice Shop room, which does not cover CSRF. The lab room named "CSRF" must have its exact content confirmed before the session[cite: 2].

Definition

CSRF is an attack that tricks an authenticated victim's browser into submitting an unwanted, state-changing request to a web application in which the victim is currently logged in. It exploits the trust the application places in the victim's browser and session, rather than in the victim's explicit intent[cite: 2].

Trust model

The web application trusts the victim's browser, not the victim's intent. Once the victim is logged in, the browser automatically attaches the session cookie to every outgoing request to that domain, including requests triggered by an attacker's page. The application cannot distinguish a request the user deliberately made from a request the attacker silently triggered[cite: 2].

Preconditions for a successful attack

  1. The target application relies on session cookies or credentials that the browser sends automatically[cite: 2].
  2. The application performs a state-changing action based solely on a valid session, without any additional per-request proof of intent[cite: 2].
  3. The attacker can predict all parameters needed for the request, or the request works with parameters the attacker controls[cite: 2].

Attack flow

Step Stage What happens
1 Victim logged in The victim has an active session on target-site.com, and the browser holds a valid session cookie (for example, sessionid=abc123)[cite: 2].
2 Victim visits attacker page The victim opens a page on attacker.com (through a phishing link, malicious ad, or embedded iframe). The page contains a hidden auto-submitting form that points at target-site.com/transfer[cite: 2].
3 Browser sends cookie silently The browser sends the forged POST to target-site.com and automatically attaches the sessionid cookie, even though attacker.com triggered the request[cite: 2].
4 Target executes the action The site receives a valid request with a valid session cookie, assumes the user intended it, and performs the transfer, email change, or password reset with the victim's privileges[cite: 2].

The lecture stresses the trust gap: the browser has no way to know the user did not intend the request, and the application has no way to know the request came from attacker.com. Both the classic exploitation pattern and the example form use an auto-submitting HTML form, or an img or fetch request, aimed at a state-changing endpoint such as a funds transfer or an email change[cite: 2].

Example forged form used in the slide:

CSRF Payload
<form action="target-site.com/transfer" method="POST"> <input name="to" value="attacker"> <input name="amount" value="1000"> </form> <script>document.forms[0].submit()</script>

Core CSRF defenses

The deck emphasises defense-in-depth: no single defense is sufficient on its own[cite: 2].

Defense How it works Notes
1. Anti-CSRF tokens A unique, unpredictable token is embedded in each form or request and validated server-side. Typically a cryptographically random value tied to the user's session. Example: a hidden input named csrf_token. The server validates it on every state-changing request[cite: 2]. Core defense[cite: 2]
2. SameSite cookie attribute SameSite=Strict or SameSite=Lax on the session cookie stops the browser sending the cookie on cross-site requests. Strict blocks all cross-site sends. Lax allows top-level GET navigations but blocks cross-site POST. Example: Set-Cookie: sessionid=abc123; SameSite=Lax; Secure; HttpOnly[cite: 2]. Browser-level defense[cite: 2]
3. Re-authentication or confirmation Requires the user to re-enter a password, or complete a 2FA challenge, before highly sensitive actions such as password change, funds transfer, or email change. GitHub asks for a password before changing the account email, and Gmail requires re-login before changing the recovery email[cite: 2]. Protects high-value actions[cite: 2]
4. Origin or Referer header check The server validates that the Origin or Referer header matches the expected domain. Example: reject the request if the origin is not https://target-site.com[cite: 2]. Supplementary only. Headers can be missing (privacy extensions, HTTPS to HTTP transitions) or stripped[cite: 2].

Rules from the slide: never rely on Origin or Referer alone, and never rely on HttpOnly alone. Combine SameSite cookies, anti-CSRF tokens, and re-authentication for sensitive actions[cite: 2].

🧠
KNOWLEDGE CHECK 5
Tests three points. The defense that most directly stops the browser sending a session cookie on a cross-site forged request is the SameSite attribute, not an anti-CSRF token or a header check. The statement that HttpOnly prevents CSRF is false, because HttpOnly only stops JavaScript reading the cookie, and the browser still sends it automatically. HttpOnly is an XSS defense against cookie theft, not a CSRF defense. The core difference between the two attacks is explained in the comparison below[cite: 2].

XSS and CSRF compared

Dimension XSS CSRF
What is executed JavaScript inside the target site's context; the attacker's script runs as the site[cite: 2]. No script runs on the target site. A forged HTTP request is sent from the victim's browser[cite: 2].
Where it runs In the victim's browser, under the origin of the vulnerable site. It can read that site's DOM, cookies, and data[cite: 2]. No code runs anywhere. The target site receives and acts on a forged request[cite: 2].
Victim requirement Visit a vulnerable page (Persistent) or click a malicious URL (Reflected). DOM XSS needs only a crafted URL fragment[cite: 2]. Be logged in to the target site and visit an attacker-controlled page[cite: 2].
Typical impact Steals cookies not marked HttpOnly, reads user data, defaces content, and performs actions as the user from within the site[cite: 2]. Forces state-changing actions with the victim's privileges, such as funds transfer, email change, password reset, or account deletion[cite: 2].
Can they chain? Stored XSS can perform a CSRF-style forced action from within the site itself. Requests then originate from the site's own origin, which bypasses SameSite and Origin or Referer checks[cite: 2]. See XSS column[cite: 2].

Memory aid: XSS = run script AS the site. CSRF = send request AS the user. The two attacks exploit different trust boundaries[cite: 2].

PART 7

Real-World Case Studies

#

Four publicly documented incidents illustrate the lecture's concepts[cite: 2].

Case What happened Lesson
Samy worm, MySpace (2005)[cite: 2] Samy Kamkar injected a Persistent XSS payload into his MySpace profile. When any logged-in user viewed the profile, the payload silently added Samy as a friend and copied itself into the viewer's profile. Over one million profiles were infected within 24 hours, the fastest-spreading worm at the time[cite: 2]. Stored XSS can be weaponised into a self-propagating worm, needing nothing more than a page view[cite: 2].
TweetDeck XSS worm, Twitter (2014)[cite: 2] A stored payload hidden in a tweet retweeted itself whenever a TweetDeck user viewed it. The payload used a heart character to break out of an HTML attribute and inject a script that retweeted the original tweet. Twitter took TweetDeck offline temporarily[cite: 2]. A single character of unsanitised input in a tweet body can become a self-propagating worm[cite: 2].
Netflix queue CSRF (2006)[cite: 2] Daniel Stamm publicly demonstrated a malicious page that silently added DVDs to a logged-in victim's Netflix queue and changed the shipping address. Netflix relied solely on the session cookie to authorise queue changes, with no anti-CSRF token. The demonstration helped drive OWASP's CSRF awareness campaign[cite: 2]. Any state-changing endpoint protected only by a session cookie is CSRF-vulnerable[cite: 2].
Yamanner worm, Yahoo Mail (2006)[cite: 2] A stored XSS payload in a Yahoo Mail email body stole the victim's address book and forwarded itself to all contacts. The worm combined XSS, which gave code execution inside Yahoo's origin, with a CSRF-style forced send[cite: 2]. XSS can chain with CSRF. Once an attacker has script execution inside the site, SameSite and Origin or Referer defenses are bypassed[cite: 2].

PART 8

Common Misconceptions

#

The lecture closes its content with three myths that cause real security failures[cite: 2].

Myth Reality
"XSS is just annoying popups."[cite: 2] XSS enables session hijacking (stealing cookies not marked HttpOnly), data theft (reading the DOM, localStorage, and API responses), account takeover (performing actions as the user), on-page keylogging, and internal network pivoting. Samy, Yamanner, and TweetDeck all started from something as simple as a single alert[cite: 2].
"A Referer check equals CSRF defense."[cite: 2] The Referer header can be missing entirely, because of browser privacy modes, HTTPS to HTTP transitions, referrer-policy=no-referrer, or stripping by network intermediaries. Relying on it alone breaks legitimate users while leaving edge-case attackers through. Use it only as a supplementary defense, combined with SameSite cookies and anti-CSRF tokens[cite: 2].
"HttpOnly stops CSRF."[cite: 2] HttpOnly prevents JavaScript from reading the cookie value, for example through document.cookie. The browser still sends the cookie automatically on every cross-site request, including forged CSRF requests. HttpOnly is an XSS defense. For CSRF, use SameSite and anti-CSRF tokens[cite: 2].

SCENARIO

Integrated Scenario and Model Answer

#

The end-of-lecture scenario describes a web application with three features[cite: 2]:

  1. A comment field that stores and later displays user input unmodified, used by other visitors[cite: 2].
  2. A search bar that reflects the search term back into the page without encoding[cite: 2].
  3. A funds-transfer form that checks only for a valid session cookie, with no additional token[cite: 2].

Students attempt three tasks: (a) name the vulnerability class for each issue; (b) write a real payload or technique for the comment field and the search bar, using the methods taught in the lecture; and (c) explain why the transfer form is vulnerable and which single defense would most directly fix it[cite: 2].

Model answer

  • Comment field: Persistent (stored) XSS. The server stores the payload and renders it for every visitor[cite: 2].
  • Search bar: Reflected XSS. The payload travels in the request and is reflected back unsanitised, firing when the specific user submits the search[cite: 2].
  • Funds-transfer form: Cross-site request forgery. The form authorises a state-changing action based solely on the auto-attached session cookie, which satisfies all three CSRF preconditions[cite: 2].

For both XSS vectors the same payload works: <iframe src="javascript:alert(`xss`)">. For the comment field, inject it, submit, and revisit the page or have another visitor view it, because the payload is stored server-side. For the search bar, paste it into the search and submit, because the server reflects the term back and the browser executes it. Only the injection point differs[cite: 2].

On the transfer form, the vulnerability is explained through the three preconditions: the browser sends the cookie automatically, the action depends only on a valid session, and the attacker can predict the recipient and amount. A logged-in victim visiting an attacker-controlled page would have the session cookie attached to a forged transfer[cite: 2].

Note: the final "single defense that most directly fixes it" entry is cut off in the source deck, so the slide does not confirm an answer. Based on the rest of the lecture, the expected answer is an anti-CSRF token validated server-side. SameSite cookies are also an acceptable answer, since they stop the cookie being sent on cross-site requests[cite: 2].

Lab Preparation, Summary, and Terminology

#

Lab Preparation and Pitfalls

The XSS reference card condenses the three verified techniques. Each has a single payload and a short sequence[cite: 2]:

Technique Vector Steps
1. DOM XSS[cite: 2] Search bar; iframe payload[cite: 2] Locate the search bar, paste the payload, submit. The browser executes the javascript: URI and the alert fires[cite: 2].
2. Persistent XSS[cite: 2] True-Client-IP header; True-Client-IP: <iframe src="javascript:alert(`xss`)">[cite: 2] Log in, open the Last Login IP page. Enable Burp interception ON, log out, add the header, forward. Log back in and revisit the page[cite: 2].
3. Reflected XSS[cite: 2] Tracking-page id parameter; ?id=<iframe src="javascript:alert(`xss`)">[cite: 2] Log in, open Order History, click the tracking icon. Replace the id value with the payload, submit the modified URL, and refresh[cite: 2].

The room recommends completing the free TryHackMe rooms "Burp Suite Basics" and "Burp Suite Repeater" first. The pitfalls slide gives three troubleshooting notes, taken from the room[cite: 2]:

  • XSS tasks not working: clear cookies and site data for the Juice Shop domain only, through the browser's clear browsing data settings[cite: 2].
  • Flag fails to display: temporarily disable Burp interception after task completion, then refresh. The room describes this as a known Burp and flag-display interaction, not an application bug[cite: 2].
  • App slow to load: the Juice Shop app can take two to five minutes to load. Wait at least five minutes before reporting it as broken[cite: 2].

Summary of Key Takeaways

  1. XSS is attacker-run JavaScript in a web application. It has three types: DOM (browser-side, iframe), Persistent (stored server-side, for example via True-Client-IP), and Reflected (single request, for example via the id parameter)[cite: 2].
  2. The same payload primitive, an iframe with a javascript: URI, works across all three types. Only the injection vector changes[cite: 2].
  3. Persistent XSS injection points are not limited to form fields. HTTP headers such as True-Client-IP and X-Forwarded-For are equally valid vectors[cite: 2].
  4. CSRF sends a forged request from the victim's browser, exploiting the application's trust in the session cookie. No script runs on the target site[cite: 2].
  5. The core CSRF defenses are anti-CSRF tokens, SameSite cookies, and re-authentication for sensitive actions. Origin and Referer checks are supplementary only[cite: 2].
  6. Juice Shop also demonstrates Injection (Week 4), Broken Authentication (Weeks 7 and 10), Sensitive Data Exposure (Week 9), and Broken Access Control (Week 7). These are not in scope this week[cite: 2].

Key Terminology

Term Definition
XSS Cross-Site Scripting. Attacker-run JavaScript in a web application's context[cite: 2].
DOM (special) XSS that executes through the HTML environment, using script or iframe tags. Runs entirely client-side[cite: 2].
Persistent XSS JavaScript that runs when the server loads a page containing it. The payload is stored, for example in a database, and fires for every visitor[cite: 2].
Reflected XSS JavaScript that runs client-side. The payload travels in the request URL or form and is reflected back unsanitised[cite: 2].
XFS Cross-Frame Scripting. An alias for the iframe and javascript: URI technique used for DOM XSS[cite: 2].
True-Client-IP HTTP header, similar to X-Forwarded-For, that tells the server or proxy the client's IP. A vulnerable injection vector for Persistent XSS[cite: 2].
CSRF Cross-Site Request Forgery. A forged request from the victim's browser that exploits session-cookie trust[cite: 2].
Anti-CSRF token A unique, unpredictable token embedded per form or request and validated server-side[cite: 2].
SameSite A cookie attribute (Strict or Lax) that stops the browser sending the cookie on cross-site requests[cite: 2].
HttpOnly A cookie attribute that stops JavaScript reading the cookie value. An XSS defense, not a CSRF defense[cite: 2].
